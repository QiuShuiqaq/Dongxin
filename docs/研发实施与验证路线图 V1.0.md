# 东信浴霸 AI 研发实施与验证路线图 V1.0

更新日期：2026-09-14
当前主线：ESP32-C3唯一业务主控 + CI1302语音前端

## 1. 推进原则

硬件主线优先于生产平台。每个阶段只用同级证据验收：网页成功不能替代C3日志，C3虚拟状态不能替代板级电平，低压LED不能替代真实负载，真实动作也不能替代电气安全和认证。

当前无需自行采购麦克风、扬声器、功放或裸CI模块；东信根据本项目协议制作完整样板。开发侧仍建议准备3.3V USB-TTL、8通道24MHz以上逻辑分析仪、数字万用表和杜邦线，用于样板故障定位。

## 3. G2当前交付

- 产品硬件能力矩阵，可区分已启用、可选和不支持；
- CI1302语音版本，包含唤醒词、固定命令、语义ID、资源包SHA和发布状态；
- CI1302事件模拟，可验证语义ID到C3意图和设备状态；
- 设备命令能力检查，不支持能力返回 `UNSUPPORTED`；
- C3/CI通信协议、安全状态机、样板要求和交付清单；
- 旧MCU串口代码保留为历史兼容资产。

## 4. G3：无样板先完成的软件

固件内部统一调整为：

```text
MQTT / CI1302 / BLE墙面板和遥控器 / 定时器
                │
                ▼
          unified_command_queue
                │
                ▼
        safety_state_machine
                │
                ▼
         device_controller
                │
                ▼
     virtual_hal / direct_control_hal
```

必须覆盖的桌面/板上测试：

1. 上电全关；
2. 取暖前风机启动；
3. 弱暖/强暖切换；
4. 关闭取暖后的散热延时；
5. 风机/换气冲突；
6. 目标温度30至45℃边界；
7. NTC开路、短路和过温；
8. IO扩展器失联；
9. 待机、超时、重复命令和过期命令；
10. OPTIONAL能力返回UNSUPPORTED；
11. 干燥模式中止和最长运行；
12. 安全事件优先于语音/云端命令。

完成G3后，C3 SuperMini仍用虚拟HAL跑MQTT真实链路；不能把虚拟HAL结果称为真实负载完成。

## 5. G4：板级驱动顺序

1. 根据东信原理图建立量产板profile，不在通用代码写死GPIO；
2. 验证3颗PCF8574上电全关写入、地址、读回、共享INT和I2C断线关断；
3. 用低压LED验证照明、风机、换气、弱暖、强暖和摆风输出时序；
4. 接入NTC，先用固定电阻/电阻箱验证ADC曲线和故障范围；
5. 接入BLE墙面板和手持遥控器，验证绑定、语义命令、回执、状态同步、连按和重连；
6. 接入摆叶电机，冻结相序、步进节拍和归零；
7. 连续切换和WiFi并发压力测试。

## 6. G5：CI1302验证顺序

1. CI独立烧录和官方自检；
2. C3/CI UART0 115200bps完成HELLO、资源版本和心跳；
3. “小东小东”分句唤醒；
4. “小东小东打开暖风”连续唤醒命令；
5. 离线命令语义ID和提示音；
6. 未命中、低置信度和VAD超时；
7. 断网固定提示；
8. I2S 16kHz/16bit/单声道PCM上行到C3并提交服务器ASR；
9. 服务器TTS经C3转换为同格式PCM，下行到CI播放；
10. 半双工、重复帧、坏CRC、拔线和双方重启；
11. 8小时音频/联网并发压力；
12. CI厂商升级流程中断和可恢复性。

CI SDK的厂商帧与本项目协议必须形成映射表。后台修改唤醒词/命令后，只有生成新资源包并完成样机验证、审核和发布才对离线识别生效。

## 7. G6/G7：东信样板

空载顺序：烧录 → 上电全关 → UART/I2S/I2C/ADC → CI语音 → BLE墙面板/遥控器 → LED输出 → 故障注入。

真实负载顺序：照明 → 吹风 → 换气 → 摆风 → 弱暖 → 强暖 → 恒温 → 干燥。接220V和执行温升测试必须由东信硬件人员负责。

软件过温阈值、散热时间、风路切换死区、摆风参数和干燥热节拍只在G7根据实测冻结。

## 8. G8：在线AI与成本

```text
CI音频 → C3 → 在线ASR → 明确规则
                         ├─ 控制：结构化意图
                         ├─ 知识库：售后回答
                         └─ 未命中：LLM
                                ↓
                        统一安全校验
                         ├─ MQTT控制
                         └─ TTS/缓存音频
```

每轮记录离线命中率、规则命中率、知识库命中率、LLM调用率、ASR/LLM/TTS费用、P95延迟和失败原因。只有在正确率和稳定性满足同一标准后才比较价格。

## 9. G10：生产平台

本地平台验证通过后迁移：阿里云IoT、RDS PostgreSQL/MySQL、Redis、内部账号权限、微信登录、BLE配网、机身二维码绑定、每机密钥、审计、90天文本清理、监控、备份和灰度发布。

第一版保持单设备单归属，不做家庭和多人共享。原始音频不落库。

## 10. 每轮固定流程

1. 选择一个Gate和明确用例；
2. 写出输入、期望、设备/版本和安全前提；
3. 实现最小代码；
4. 类型检查/构建/单元测试；
5. 烧录或启动服务；
6. 收集串口、MQTT、API、波形和状态证据；
7. 记录失败和阻塞项；
8. 同级证据全部通过后进入下一Gate。

## 11. 当前立即执行顺序

1. 在C3 SuperMini上回归G3：MQTT真实命令、风机预启动、互锁、散热、最长运行和重复命令；
2. 为G3补齐可缩短时间参数的板上自测和故障注入，不把虚拟HAL当成负载验证；
3. 东信按《东信样板硬件接口及验收要求 V1.0》提交原理图、引脚表和BOM，双方确认后投板；
4. 取得CI1302 SDK/资源工具以及BLE终端芯片SDK，分别开始协议适配；
5. 平台补齐语音资源导出、BLE事件模拟、测试记录和样板Gate结果；
6. 样板到件后依次执行G4至G7；
7. 硬件等待期并行完善在线ASR/TTS、成本回归和服务端临时音频会话；
8. 硬件与AI链路稳定后进入生产平台。
