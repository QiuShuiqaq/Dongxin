# CI1302 独立开发板 USB 观察记录

日期：2026-10-30。状态：仅验证电脑侧识别和调试串口接收；未接入 STM32，未烧录新固件，未测试负载动作。

## 当前实物连接

```text
CI1302 开发板 -- 独立 USB / CH340 / COM6 -- 电脑
ESP32-C3 开发板 -- CH343 / COM5 -- 电脑
ESP32-C3 -- 现有 UART -- 样机 STM32 -- J-Link / USB -- 电脑
```

Windows 设备信息显示 `COM6 = USB-SERIAL CH340 (VID_1A86&PID_7523)`，`COM5 = USB-Enhanced-SERIAL CH343 (VID_1A86&PID_55D3)`，J-Link 单独枚举。没有任何 CI1302 至 STM32/C3 的数据线。

## 本轮观察与限制

- 在 `COM6` 以 `921600/8N1`、DTR/RTS 关闭、只接收方式观察 12 秒，收到 323 字节。可辨识内容包含任务表、`decoder_manage_`、`audio_in_manage` 和 `Heap left: 244KB`。未向串口发送数据。
- 官方 CI13XX 文档说明：烧录用 UART0 默认可输出日志，日志波特率为 921600；标准应用串口协议默认使用 UART1、9600。现有 `COM6` 观测到的是日志，不能把它没有出现应用命令帧解释成 CI 没有识别或没有输出 UART1 帧。
- 本轮没有在监听期间进行人为唤醒或命令词测试；没有测得唤醒、识别结束、未命中事件及其时序。任务表出现的原因也不能仅凭本次日志判定为板卡复位。
- 目前板上仍是用户验证过可播报的出厂“智能管家”固件。`offline-control.words.json` 与 V0.2 工作簿只是候选配置，尚未导入、生成固件或烧录；不能用它们的 `A5 FA ...` 帧去解释出厂固件的实际输出。
- 手头 `CI-B02-MB开发板套件说明.pdf` 使用的是旧模块型号，不应作为当前 `CID02GS02S / CI-B02-MB-V30` 的接线依据。接入 UART1 前须核对当前板卡丝印、原理图和 3.3V 电平。

## 下一轮无负载验证

1. 研发中心的“语音验证 → CI1302 实板”已提供本机只读监听：`UART1 · 指令帧 · 9600` 选择 USB-TTL 转换器当前的 `COM7`；`UART0 · 调试日志 · 921600` 选择 CI 板自身 USB 当前的 `COM6`。开始后由操作者说出厂唤醒词“智能管家”和一个出厂固定词，停止后核对原始字节、候选 V1 帧并导出 JSON。每次完成的记录保存在 `D:\workspace\Dongxin\.artifacts\ci1302-monitor`，只含串口数据、不含录音；此目录不提交 Git。
2. 目前用户已按官方 V30 板接口将独立 USB-TTL 接至 J4：`TX1 → 转换器 RXD`、`GND → 转换器 GND`；接口电平需保持 3.3V，不接转换器 5V/3V3/TXD。新转换器枚举为 `COM7`。先前短时监听收到 0 字节，但当时操作者没有说唤醒词，因此不能据此评价识别输出。新一轮须在页面显示“正在监听”后再说话。
3. 出厂固件是否从 UART1 发识别结果尚未验证；即使 CI 有清晰播报且 COM7 为 0 字节，也需先核对接线和实际固件通信配置，不得直接认定 CI 硬件失效。研发中心的“V1 候选帧”只是对符合 8 字节加和校验的原始字节作诊断，不等于已经验证了项目自定义协议或 STM32 动作。
4. 确认候选工作簿的唤醒词播报模式。若要支持“小东小东打开照明”连续说，立即主动播报“我在”可能遮住后半句；需验证平台是否允许唤醒反馈延后或改由主控触发。没有验证前不将 V0.2 视为最终固件。
5. 获得真实 UART1 帧及时间记录之后，再冻结 CI→STM32 协议、STM32→C3 唤醒/命中事件，并开展音频预录和同句防重复联调。

参考：启英泰伦《CI13XX 系列芯片串口协议 V2》《UART 串口调试工具使用说明》；项目《CI1302 经 STM32 接入与在线离线协同 V1.0》。
