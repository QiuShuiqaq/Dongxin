# 东信智能浴霸 AI 大模型融合创新项目技术实施与报价明细 V1.0

## 一、文档用途

本文件用于说明本项目 38,800 元实施服务费用对应的具体技术工作量，作为学校、导师和项目内部沟通时的支撑材料。

本文件与《东信智能浴霸 AI 大模型融合创新项目实施服务报价说明 V1.0》保持同一报价总额。对外沟通可优先使用报价说明文件；需要解释系统实现内容、开发范围和工作量时，可使用本文件。

## 二、项目技术线路

本项目按“AI Gateway + 企业后台 + 微信小程序 + 设备接入接口”的方式实施。

| 系统部分 | 当前开发线路 | 主要作用 |
|---|---|---|
| AI 服务端 | `apps/api` | 设备接入、语音文本处理、大模型调用、知识库问答、安全规则、日志和费用统计 |
| 企业后台 | `apps/web` | 给东信内部测试使用，管理模型、测试集、设备、知识库、主动沟通、日志和费用 |
| 微信小程序 | `apps/miniapp` | 面向现场演示和消费者端验证，支持设备状态、控制、AI 问答 |
| 共享类型 | `packages/shared` | 统一三端数据结构、设备动作、测试结果、模型配置和接口契约 |
| 开发数据 | `data` | 保存模型配置、测试语料、评测记录、知识库资料和设备状态等研发数据 |
| 技术文档 | `docs` 及项目根目录文档 | 保存系统设计、设备接入协议、测试方案和交付说明 |

整体链路：

```text
语音模块 / 小程序 / 企业后台
        |
        v
QiuAI AI Gateway
        |
        |-- 简单规则匹配
        |-- LLM 意图识别
        |-- 知识库问答
        |-- 主动沟通策略
        |-- 安全规则校验
        |-- Token 和费用记录
        |
        v
设备接入层
        |
        v
WiFi 模块
        |
        v
浴霸主控板 / MCU
```

## 十二、费用统计口径

系统内费用统计分为两类：

| 类型 | 用途 | 说明 |
|---|---|---|
| 测试费用 | 研发评测使用 | 意图测试和模型评测产生的 token、费用和结果对比 |
| 生产费用 | 真实设备运行使用 | 样机或后续设备真实运行链路产生的 LLM 调用费用 |

这样设计的目的：

1. 研发阶段可以清楚看到测试模型消耗；
2. 真实设备运行费用和测试费用分开统计；
3. 后续向东信解释量产成本时有真实数据依据；
4. 可以按 10 万台年销量规模进行成本估算。

| 主动沟通 | M5 | 人感/雷达事件触发并返回播报和确认流程 |
| 企业后台 | M4 | 页面功能可用，数据可查看 |
| 微信小程序 | M6 | 可查看状态、控制设备和 AI 问答 |
| 测试资料 | M7 | 提交测试记录、问题清单和部署说明 |

## 十五、实施风险和处理方式

| 风险 | 影响 | 处理方式 |
|---|---|---|
| 样机提供延迟 | 影响真实联调时间 | 先用模拟设备接口开发，样机到位后集中联调 |
| 主控协议调整 | 影响控制映射 | 保持云端动作模型稳定，只调整设备适配层 |
| 语音识别文本不稳定 | 影响意图识别准确率 | 增加规则和测试语料，问题归档给语音模块侧排查 |
| 模型返回不稳定 | 影响控制可靠性 | JSON 校验、安全规则、兜底话术和模型替换 |
| 知识库资料不足 | 影响售后问答效果 | 缺失问题标记，不编造答案 |
| 第三方 API 费用增加 | 影响成本预估 | 后台记录真实 token 和费用，及时调整模型和规则策略 |

## 十六、正式实施系统组成展开

本项目不是单独接一个模型接口，也不是只做一个演示页面。正式实施时，需要把 AI 服务端、企业后台、小程序、设备接入接口和数据存储串成一套可以联调、可记录、可追溯、可部署的系统。

| 系统组成 | 实施内容 | 作用 | 对应报价模块 |
|---|---|---|---|
| AI Gateway 网关服务 | 接收语音文本、小程序请求、后台测试请求和设备事件，统一完成规则判断、模型调用、安全校验和响应生成 | 整个 AI 控制链路的核心服务 | M2、M3 |
| 设备接入服务 | 设备注册、心跳、状态上报、事件上报、命令轮询、执行回执 | 支撑真实样机与服务器联调 | M3 |
| 企业后台 | 模型配置、意图测试、测试集管理、设备管理、知识库、主动沟通、日志和费用统计 | 给东信内部测试、运维和研发验证使用 | M4 |
| 小程序接口 | 设备状态、常见控制、AI 问答、知识库帮助、主动沟通设置 | 支撑现场演示和消费者端体验验证 | M6 |
| 数据库 | 保存账号、设备、状态、命令、AI 对话、模型消耗、知识库、测试集、日志等数据 | 保障系统可查、可测、可复盘 | M2、M3、M4、M5、M7 |
| 安全规则层 | 动作白名单、设备状态拦截、二次确认、输出校验、异常兜底 | 防止大模型直接控制硬件造成风险 | M2、M7 |
| 部署运行环境 | 服务器、域名、HTTPS、进程守护、日志、备份、环境变量配置 | 保证后台、小程序和设备可以真实访问 | M1、M7 |

当前系统已经具备前期研发验证基础，正式推进时应在现有代码结构上继续扩展，而不是重新开发。这样可以保留已经完成的模型测试、意图路由、设备接口和后台页面能力，同时补齐真实上线需要的数据库、安全、部署和联调细节。

## 十七、AI Gateway 网关详细设计

AI Gateway 是本项目最关键的服务端能力。它位于设备、小程序、企业后台和大模型之间，负责把用户自然语言转换为安全可执行的设备动作，或转换为适合播报和展示的简短回答。

### 17.1 请求来源

| 来源 | 典型入口 | 处理内容 |
|---|---|---|
| WiFi 语音模块 | `/api/device/v1/voice-turn` | 接收语音识别文本，返回播报文本、确认状态和设备动作 |
| 设备事件 | `/api/device/v1/events` | 接收人感、雷达、故障、运行状态变化，触发主动沟通判断 |
| 小程序 | 小程序 AI 问答和控制接口 | 处理用户手动输入、设备控制和知识库问答 |
| 企业后台 | 意图测试、批量评测、设备控制测试 | 用于模型选型、测试集评测和联调验证 |

### 17.2 语义处理流程

```text
接收输入
  |
  v
基础校验：设备编号、来源、文本长度、状态参数
  |
  v
简单规则优先匹配
  |
  |-- 命中明确控制指令：生成结构化动作
  |-- 命中常见问答：返回固定或知识库回答
  |-- 未命中或表达复杂：进入 LLM
  v
LLM 意图识别或知识库问答
  |
  v
JSON 结构校验
  |
  v
安全规则校验
  |
  |-- 可执行：写入设备命令
  |-- 需要确认：返回确认话术
  |-- 拒绝执行：返回兜底说明
  v
记录日志、token、费用、耗时和结果
```

### 17.3 简单规则与 LLM 分流

为了控制模型调用费用，第一阶段不把所有请求都交给大模型处理。网关先做本地规则判断，只有规则无法稳定判断时再调用 LLM。

| 类型 | 示例 | 处理方式 |
|---|---|---|
| 明确控制 | “打开灯”“关闭换气”“开弱暖” | 本地规则直接生成动作，不调用 LLM |
| 明确状态问答 | “现在温度多少”“浴霸开着吗” | 读取设备状态后直接回答 |
| 常见售后问答 | “怎么清洁滤网”“故障码 E1 是什么” | 优先走知识库检索 |
| 复杂表达 | “我洗澡有点冷，帮我弄舒服一点” | 调用 LLM 判断意图和动作 |
| 情绪化表达 | “今天好累，洗澡的时候舒服点” | 调用 LLM 生成简短回应，再结合安全规则判断是否建议动作 |
| 高风险表达 | “一直开强暖”“不要管温度一直加热” | 进入安全规则，必要时拒绝或要求确认 |

### 17.4 统一结果模型

网关输出需要统一，不让设备端、小程序和后台分别理解不同格式。

```json
{
  "resultType": "CONTROL | ANSWER | CONFIRM | REJECT | ERROR",
  "replyText": "好的，已为你打开弱暖。",
  "actions": [
    {
      "target": "heater",
      "command": "setLevel",
      "value": "weak"
    }
  ],
  "needConfirm": false,
  "safety": {
    "passed": true,
    "reason": ""
  },
  "usage": {
    "provider": "deepseek",
    "model": "deepseek-chat",
    "promptTokens": 120,
    "completionTokens": 35,
    "cost": 0.00012
  }
}
```

### 17.5 模型供应商统一接入

模型接入层需要支持多个国内供应商，方便东信根据测试结果选择成本、稳定性和回答质量更合适的模型。

| 能力 | 实施要求 |
|---|---|
| 统一配置 | 后台维护供应商、模型名称、Base URL、启用状态、价格口径、超时时间 |
| API Key 管理 | API Key 只保存在服务端，不进入小程序、设备端和前端静态代码 |
| 统一调用 | 对 OpenAI-compatible 接口进行封装，减少切换模型时的代码改动 |
| 返回校验 | 第三方模型返回必须经过 JSON Schema 校验，不能直接进入设备控制 |
| 异常兜底 | 超时、限流、余额不足、返回格式异常时，统一返回可播报的失败说明 |
| 费用记录 | 每次调用记录输入 token、输出 token、耗时、费用和使用场景 |

### 17.6 安全规则引擎

大模型只负责理解和生成候选结果，不能直接控制浴霸。设备动作必须经过安全规则层。

| 规则类型 | 示例 |
|---|---|
| 动作白名单 | 只允许照明、弱暖、强暖、换气、吹风、摆风、待机、温度调节等已确认动作 |
| 设备状态限制 | 设备离线、故障码存在、状态未知时，不执行高风险动作 |
| 高风险确认 | 强暖、长时间运行、温度上调等动作可要求用户二次确认 |
| 频率限制 | 主动沟通、重复控制、连续失败请求需要限制频率 |
| 文本限制 | 播报文本控制在简短范围内，避免长文本影响语音体验 |
| 兜底策略 | 模型不确定、返回异常或命令不合法时，不下发控制指令 |

## 十八、数据库设计

当前研发阶段可以使用本地 JSON 文件快速保存配置和测试数据，正式部署到东信服务器后，应切换为数据库存储。数据库不是简单的“保存数据”，而是支撑设备联调、费用透明、测试复盘、知识库维护和后续产品上线的基础。

### 18.1 数据库选型

正式实施建议优先采用 MySQL 8.0。原因是企业服务器部署普遍、运维成本低、技术人员容易接手，足以覆盖本阶段设备接入、后台、小程序和测试数据存储需求。若东信已有 PostgreSQL 或其他数据库环境，也可以按现有环境适配。

| 项目 | 设计口径 |
|---|---|
| 研发阶段 | `data` 目录本地 JSON 存储，便于快速调试 |
| 正式部署 | MySQL 8.0 或甲方服务器已有数据库 |
| 数据访问 | 后端统一 Repository 层，避免业务代码直接依赖具体存储方式 |
| 迁移方式 | 将模型配置、测试集、知识库、设备数据从 JSON 迁移到数据库 |
| 备份方式 | 每日数据库备份，关键配置变更保留操作记录 |

### 18.2 数据表总览

| 数据表 | 用途 | 关键字段 | 索引和说明 |
|---|---|---|---|
| `admin_users` | 企业后台账号 | `id`、`name`、`phone`、`role`、`password_hash`、`status`、`created_at` | `phone` 唯一索引，用于后台登录 |
| `miniapp_users` | 小程序用户 | `id`、`openid`、`unionid`、`nickname`、`status`、`created_at` | `openid` 唯一索引 |
| `devices` | 设备基础信息 | `id`、`device_sn`、`model`、`firmware_version`、`protocol_version`、`status`、`last_seen_at` | `device_sn` 唯一索引 |
| `device_bindings` | 用户与设备绑定关系 | `id`、`device_id`、`user_id`、`bind_role`、`bound_at`、`unbound_at` | `device_id`、`user_id` 联合索引 |
| `device_states` | 设备状态快照 | `device_id`、`power`、`mode`、`temperature`、`humidity`、`human_present`、`fault_code`、`reported_at` | `device_id + reported_at` 索引 |
| `device_events` | 设备事件 | `device_id`、`event_type`、`payload_json`、`occurred_at` | 用于雷达、人感、故障和运行事件追溯 |
| `device_commands` | 云端下发命令 | `device_id`、`source`、`actions_json`、`status`、`safety_result`、`issued_at`、`executed_at` | 支撑命令轮询和执行回执 |
| `voice_sessions` | 语音交互回合 | `device_id`、`input_text`、`route_type`、`result_type`、`reply_text`、`created_at` | 用于追踪每句话的处理链路 |
| `ai_interactions` | 大模型调用记录 | `session_id`、`provider_id`、`model`、`input_text`、`output_json`、`latency_ms`、`status` | 记录模型原始结果和解析结果 |
| `model_providers` | 模型配置 | `provider_key`、`model_name`、`base_url`、`price_json`、`enabled`、`timeout_ms`、`api_key_ref` | 不直接明文保存密钥 |
| `model_usage_logs` | token 和费用明细 | `usage_type`、`provider`、`model`、`prompt_tokens`、`completion_tokens`、`total_cost`、`created_at` | 区分测试费用和生产费用 |
| `prompt_versions` | 提示词版本 | `scene`、`version`、`content`、`status`、`published_at` | 便于模型效果回溯 |
| `test_sets` | 测试集 | `name`、`type`、`description`、`case_count`、`created_at` | 支持标准、简单、复杂、自定义测试集 |
| `test_cases` | 测试语料 | `test_set_id`、`category`、`input_text`、`expected_json`、`expected_type`、`tags` | 支持分类筛选和批量评测 |
| `evaluation_runs` | 批量评测任务 | `test_set_id`、`provider_id`、`model`、`started_at`、`finished_at`、`summary_json` | 用于多模型、多轮测试对比 |
| `evaluation_items` | 单条评测结果 | `run_id`、`case_id`、`actual_json`、`passed`、`latency_ms`、`token_usage_json`、`cost` | 用于准确率和成本计算 |
| `knowledge_documents` | 知识库文档 | `title`、`category`、`content`、`source`、`status`、`updated_at` | 后台维护产品资料 |
| `knowledge_chunks` | 知识库分段 | `document_id`、`chunk_text`、`keywords`、`sort_order` | 支撑检索和问答引用 |
| `knowledge_queries` | 知识库问答记录 | `question`、`answer`、`matched_document_ids`、`confidence`、`created_at` | 用于补充资料和优化问答 |
| `proactive_settings` | 主动沟通配置 | `device_id`、`enabled`、`mode`、`quiet_hours_json`、`frequency_limit_json` | 支持用户关闭和模式调整 |
| `proactive_events` | 主动沟通触发记录 | `device_id`、`trigger_type`、`decision`、`reply_text`、`confirmed`、`created_at` | 记录触发、播报、确认和动作 |
| `system_logs` | 系统日志 | `level`、`module`、`message`、`context_json`、`created_at` | 后台查看错误和运行记录 |
| `security_audit_logs` | 安全审计 | `actor_type`、`actor_id`、`action`、`resource`、`ip`、`created_at` | 记录登录、配置、密钥和关键操作 |

### 18.3 关键表说明

`devices` 是设备接入的主表，设备注册、心跳、状态上报、命令轮询都需要围绕设备编号展开。正式联调时，东信 WiFi 模块需要使用稳定的 `device_sn`，服务端根据该编号识别设备、返回配置并记录状态。

`device_states` 用于保存设备状态。照明、取暖、换气、摆风、温度、湿度、人感和故障码都应进入状态表。后台、小程序和安全规则层都以该表的最新状态作为判断依据。

`device_commands` 用于保存云端下发命令。每条命令要记录来源、动作内容、安全校验结果、下发时间、过期时间、执行状态和设备回执。这样现场联调时可以判断问题发生在 AI 理解、服务端下发、WiFi 模块接收还是 MCU 执行。

`ai_interactions` 和 `model_usage_logs` 用于拆分“模型效果”和“模型费用”。前者记录模型输入输出、解析结果和耗时，后者记录 token 和成本。这样可以分别回答两个问题：模型是否好用，调用是否便宜。

`test_sets`、`test_cases`、`evaluation_runs`、`evaluation_items` 是意图测试的核心表。标准测试集、1000 条简单测试集、1000 条复杂测试集和自定义导入测试集都应落在这一组表里。

`knowledge_documents` 和 `knowledge_chunks` 支撑企业知识库。第一阶段可以先做文档分段和关键词检索，后续如需要更强语义检索，可在该结构上增加向量字段或独立向量索引，不影响后台资料维护方式。

### 18.4 数据库索引和保留策略

| 数据类型 | 索引重点 | 保留策略 |
|---|---|---|
| 设备状态 | `device_id + reported_at` | 保留最近状态和必要历史记录 |
| 设备命令 | `device_id + status`、`issued_at` | 保留联调和问题追溯需要的记录 |
| 模型调用 | `provider + model + created_at` | 用于按模型统计费用和效果 |
| 评测结果 | `run_id + case_id` | 保留完整评测记录，便于生成对比图表 |
| 知识库 | `category`、`status`、`updated_at` | 保留当前有效资料和更新记录 |
| 安全审计 | `actor_type + created_at` | 关键操作长期留痕 |

## 十九、接口与数据契约

本项目涉及设备、后台、小程序和第三方模型。接口必须先统一数据结构，再进入联调。否则样机联调时很容易出现字段含义不一致、错误无法定位、前端和设备端各自适配的问题。

### 19.1 统一响应格式

后台和小程序接口建议采用统一响应格式：

```json
{
  "success": true,
  "data": {},
  "error": null,
  "requestId": "req_20260817_0001",
  "timestamp": "2026-08-17T10:00:00+08:00"
}
```

错误响应统一为：

```json
{
  "success": false,
  "data": null,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "请求参数不合法",
    "details": {}
  },
  "requestId": "req_20260817_0002",
  "timestamp": "2026-08-17T10:00:00+08:00"
}
```

### 19.2 错误码口径

| 错误码 | 说明 |
|---|---|
| `VALIDATION_ERROR` | 请求字段缺失、类型错误或超出范围 |
| `UNAUTHORIZED` | 未登录或设备认证失败 |
| `FORBIDDEN` | 没有权限操作该设备或配置 |
| `DEVICE_OFFLINE` | 设备离线，不能执行控制 |
| `DEVICE_FAULT` | 设备存在故障状态，拦截高风险动作 |
| `MODEL_TIMEOUT` | 大模型调用超时 |
| `MODEL_INVALID_OUTPUT` | 模型返回格式不符合结构化要求 |
| `SAFETY_REJECTED` | 安全规则拒绝执行 |
| `COMMAND_EXPIRED` | 设备命令已过期 |
| `INTERNAL_ERROR` | 服务端异常 |

### 19.3 设备接入接口

| 接口 | 方向 | 主要字段 | 说明 |
|---|---|---|---|
| `/api/device/v1/register` | 设备到服务器 | `deviceSn`、`model`、`firmwareVersion`、`protocolVersion`、`capabilities` | 设备首次接入或重置后注册 |
| `/api/device/v1/heartbeat` | 设备到服务器 | `deviceSn`、`networkStatus`、`timestamp` | 维护在线状态 |
| `/api/device/v1/config` | 设备到服务器 | `deviceSn`、`protocolVersion` | 返回轮询间隔、超时和功能配置 |
| `/api/device/v1/state` | 设备到服务器 | `power`、`mode`、`temperature`、`humidity`、`humanPresent`、`faultCode` | 上报设备当前状态 |
| `/api/device/v1/events` | 设备到服务器 | `eventType`、`payload`、`occurredAt` | 上报人感、雷达、故障和运行事件 |
| `/api/device/v1/voice-turn` | 设备到服务器 | `text`、`deviceState`、`sessionId` | 在线语音文本进入 AI Gateway |
| `/api/device/v1/commands/poll` | 设备到服务器 | `deviceSn`、`limit` | 设备轮询待执行命令 |
| `/api/device/v1/commands/result` | 设备到服务器 | `commandId`、`status`、`resultPayload` | 设备回传执行结果 |

### 19.4 后台接口

## 二十、安全与稳定性测试

本项目涉及真实浴霸控制，安全优先级高于创新体验。测试目标不是证明模型“会聊天”，而是证明模型输出不会绕过规则直接控制硬件。

### 20.1 安全测试范围

| 类别 | 测试内容 | 验证标准 |
|---|---|---|
| API Key 安全 | 密钥不进入前端、小程序和设备端 | 浏览器代码、网络请求和小程序包中不出现密钥 |
| 设备认证 | 未注册设备、错误签名、过期时间戳请求 | 服务端拒绝处理 |
| 参数校验 | 缺字段、错误类型、超范围温度、非法动作 | 返回统一错误，不写入命令 |
| 模型输出校验 | 非 JSON、字段缺失、动作不存在、值越界 | 不下发控制指令 |
| 安全规则 | 离线、故障、强暖、长时间运行、低置信度 | 拦截或要求二次确认 |
| 主动沟通频率 | 短时间重复进入、连续触发、夜间触发 | 按配置限制播报 |
| 日志脱敏 | API Key、手机号、openid、设备密钥 | 日志不展示完整敏感信息 |
| 费用异常 | 短时间大量请求、循环调用、模型超时重试 | 限流并记录异常 |

### 20.2 稳定性测试范围

| 场景 | 处理方式 |
|---|---|
| 大模型超时 | 返回固定兜底话术，不下发不确定动作 |
| 大模型返回格式异常 | 记录异常，返回“我没理解，请再说一遍”一类短回复 |
| 设备离线 | 后台和小程序显示离线，控制请求不进入执行状态 |
| 设备回执超时 | 命令标记为超时，保留问题追溯记录 |
| 知识库无答案 | 返回联系官方售后或查看说明书，不编造答案 |
| 小程序网络异常 | 前端提示失败，避免重复提交控制命令 |
| 后台刷新和并发测试 | 保证测试结果、费用统计和设备日志不串数据 |

### 20.3 安全边界说明

本阶段做基础应用安全和设备控制安全验证，重点覆盖接口鉴权、参数校验、密钥保护、模型输出校验、设备状态拦截和关键日志追溯。若后续进入大规模量产和公开运营，还需要根据正式部署环境增加更完整的渗透测试、等保合规评估和运维安全制度。

## 二十一、部署上线与运行配置

正式联调需要真实服务器环境。后台、小程序、设备接入接口和模型调用都应部署在服务器上，并通过 HTTPS 对外访问。

### 21.1 推荐部署结构

```text
公网域名 / HTTPS
        |
        v
Nginx 反向代理
        |
        |-- 企业后台静态页面
        |-- 小程序 API
        |-- 设备接入 API
        |-- AI Gateway API
        v
Node.js / Fastify 服务
        |
        |-- MySQL 数据库
        |-- 日志文件
        |-- 模型供应商 API
```

### 21.2 服务器配置建议

| 阶段 | 配置建议 | 说明 |
|---|---|---|
| 样机研发联调 | 2 核 CPU、4GB 内存、50GB 磁盘 | 支撑后台、小程序、少量设备和模型调用测试 |
| 小批量试运行 | 4 核 CPU、8GB 内存、100GB 磁盘 | 支撑更多日志、测试记录和并发访问 |
| 后续量产扩展 | API 服务和数据库分离，按设备量扩容 | 根据真实调用量和并发压力决定 |

### 21.3 运行配置

| 配置项 | 内容 |
|---|---|
| 服务端口 | 后端服务端口可配置，当前开发口径为 `3077` |
| 域名 | 后台、小程序接口、设备接口统一使用 HTTPS 域名 |
| 环境变量 | 数据库连接、模型 Key、JWT 密钥、设备签名密钥、日志级别 |
| 进程守护 | 使用 PM2 或 Docker Compose 保证服务异常后可自动拉起 |
| 日志 | API 请求、设备事件、模型调用、错误日志分模块保存 |
| 备份 | 数据库定期备份，模型配置、知识库资料和测试集优先备份 |

### 21.4 不同环境划分

## 二十二、测试验证体系

测试工作需要覆盖模型、设备、知识库、主动沟通、小程序和后台。测试结果应能在后台查看，并形成项目验收资料。

### 22.1 模型评测

| 测试集 | 规模 | 用途 |
|---|---:|---|
| 标准测试集 | 约 44 条 | 覆盖核心控制、问答和安全边界 |
| 简单测试集 | 约 1000 条 | 验证规则匹配命中率和低成本处理能力 |
| 复杂测试集 | 约 1000 条 | 验证 LLM 对复杂表达、模糊表达和多动作表达的理解能力 |
| 自定义测试集 | 按导入文件确定 | 支持后续根据现场问题追加测试 |

### 22.2 评测指标

| 指标 | 说明 |
|---|---|
| 意图准确率 | 模型或规则识别的意图是否符合预期 |
| JSON 有效率 | 输出是否符合结构化格式 |
| 动作准确率 | 设备动作、目标、参数是否正确 |
| 安全通过率 | 应拦截的动作是否被拦截，应确认的动作是否要求确认 |
| 平均延迟 | 单次请求从进入服务端到返回结果的耗时 |
| 平均 token | 单次请求输入和输出 token 消耗 |
| 千次成本 | 按模型官方价格计算 1000 次请求成本 |
| 失败原因分布 | 统计模型超时、格式错误、动作错误、规则拦截等原因 |

### 22.3 设备联调测试

| 测试项 | 验证内容 |
|---|---|
| 注册和心跳 | 设备能出现在后台，在线状态可更新 |
| 状态上报 | 温度、湿度、人感、模式、故障码能正确保存和展示 |
| 控制下发 | 后台、小程序、语音入口能生成命令并被设备获取 |
| 执行回执 | 设备执行成功、失败、超时能回传并记录 |
| 协议映射 | 标准动作能映射为东信主控可识别的数据格式 |
| 异常处理 | 离线、故障、协议字段缺失时不误执行 |

### 22.4 知识库和主动沟通测试

| 模块 | 测试内容 |
|---|---|
| 知识库 | 产品介绍、安装、使用、故障、售后、保养清洁问答 |
| 资料缺失 | 没有答案时不编造，提示联系官方售后 |
| 主动问候 | 人感进入触发后能生成短播报 |
| 环境提醒 | 温度低、湿度高等条件触发合理提醒 |
| 确认流程 | 涉及设备动作时先询问，用户确认后再执行 |
| 安静模式 | 在配置时间段内减少或停止主动播报 |
