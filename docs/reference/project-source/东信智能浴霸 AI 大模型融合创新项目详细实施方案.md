# 东信智能浴霸 AI 大模型融合创新项目详细实施方案

版本：V1.0  
日期：2026-08-16  
依据文件：《东信智能浴霸 AI 大模型融合创新项目需求说明书》

## 一、方案目标

本方案围绕本次 AI 落地交付展开，重点是把东信现有浴霸样机接入服务器，完成 AI 控制、主动沟通、知识库问答、企业后台、小程序展示和真实模型费用测试。

本阶段不是重新开发浴霸硬件，也不是替代东信现有主控板和离线语音模块。东信负责浴霸硬件、主控板、基础浴霸功能、离线语音芯片、样机和底层执行能力；乙方负责 AI 相关软件系统、WiFi 联网侧适配、服务器部署、模型接入、知识库、主动沟通策略、后台、小程序和联调测试。

本阶段优先级按以下顺序执行：

1. 能实现：先跑通真实样机闭环；
2. 稳定安全：大模型不直接控制硬件，所有动作经过规则校验；
3. 成本可控：简单问题不进 LLM，真实记录 token 和费用；
4. 创新体验：在稳定基础上实现主动沟通和情绪价值。

## 四、设备接入设计

### 4.1 设计原则

设备接入采用“两层协议”：

1. 云端和 WiFi 模块之间使用 JSON，方便开发、调试、日志记录和后续扩展；
2. WiFi 模块和浴霸主控板之间使用固定长度协议帧，方便 MCU 快速解析和稳定执行。

金工提到的 AXENT 协议可以作为底层协议参考。它的优点是固定字节长度、命令码清晰、校验简单、下位机读取方便。本项目不需要照搬其全部命令，但建议采用类似结构。

### 4.2 云端到 WiFi 模块 JSON

云端下发给 WiFi 模块的控制消息建议如下：

```json
{
  "requestId": "cmd_20260816_001",
  "deviceId": "DX-BATH-001",
  "source": "voice",
  "replyText": "好的，已为你打开弱暖。",
  "needConfirm": false,
  "actions": [
    {
      "code": "heater",
      "value": "weak",
      "durationMinutes": 30
    }
  ]
}
```

关键字段：

| 字段 | 说明 |
| --- | --- |
| `requestId` | 本次请求编号，用于日志和问题追踪 |
| `deviceId` | 设备编号 |
| `source` | 来源：语音、小程序、后台、主动沟通 |
| `replyText` | 返回给语音模块播报的文本 |
| `needConfirm` | 是否需要用户二次确认 |
| `actions` | 通过安全规则后的设备动作 |

### 4.3 WiFi 到 MCU 固定帧

WiFi 模块收到 JSON 后，将动作转换为固定帧下发给主控板。

建议固定 32 字节结构：

```text
Byte0      帧头 0x02
Byte1      方向码，例如 WiFi->MCU 为 0xCF，MCU->WiFi 为 0xCA
Byte2      品类码，例如浴霸 0x07
Byte3      命令码
Byte4-28   数据区，未使用填 0x00
Byte29     校验和，从 Byte2 到 Byte28 异或
Byte30     帧尾1，例如 0x0F / 0x0B
Byte31     帧尾2 0x04
```

第一阶段命令表建议：

| 功能 | 命令码 | 数据说明 |
| --- | --- | --- |
| 状态查询 | `0x00` | 无 |
| 照明 | `0x01` | `0x00` 关，`0x01` 开 |
| 换气 | `0x02` | `0x00` 关，`0x01` 开 |
| 吹风 | `0x03` | `0x00` 关，`0x01` 开 |
| 暖风 | `0x04` | `0x00` 关，`0x01` 弱暖，`0x02` 强暖 |
| 摆风 | `0x05` | `0x00` 关，`0x01` 开 |
| 除湿 | `0x06` | `0x00` 关，`0x01` 开 |
| 运行时间 | `0x09` | 0-120 分钟 |
| 模式设定 | `0x0B` | `0x00` 退出，`0x01` 进入 |
| 联网使能 | `0x0C` | `0x00` 禁止，`0x01` 使能 |
| 网络状态查询 | `0xA3` | 返回联网状态 |

以上命令码用于第一版联调草案。东信主控协议如果已有正式编码，乙方在设备适配层做映射，不影响云端 AI 逻辑。

### 4.4 设备上报数据

设备需要向服务器上报以下数据：

| 数据 | 用途 |
| --- | --- |
| 在线状态 | 判断能否下发控制 |
| 灯光、暖风、换气、吹风、摆风、待机 | 展示设备状态和判断动作结果 |
| 温度、湿度 | 主动沟通、环境提醒、AI 温度建议 |
| 是否有人 | 主动沟通触发 |
| 雷达/人感事件 | 进入、离开、持续停留 |
| 故障码 | 安全规则拦截和问题排查 |
| 控制执行结果 | 验证命令是否成功执行 |

## 五、AI 控制链路

### 5.1 处理流程

语音文本、小程序输入、后台测试语料统一进入 AI Gateway：

```text
输入文本
  |
  v
关键词和规则匹配
  |
  |-- 命中简单控制：不调用 LLM，直接生成结构化动作
  |
  |-- 未命中或复杂表达：调用 LLM
  v
结构化意图
  |
  v
安全规则校验
  |
  |-- 通过：生成设备命令
  |-- 需要确认：返回确认话术
  |-- 拦截：返回原因
  v
下发设备 / 返回播报 / 写入日志
```

### 5.2 简单规则优先

为了降低成本和提高稳定性，以下内容优先走代码规则，不进大模型：

| 类型 | 示例 |
| --- | --- |
| 明确开关命令 | 打开灯、关闭灯、打开换气、关闭换气 |
| 明确取暖命令 | 打开弱暖、打开强暖、关闭暖风 |
| 明确待机命令 | 全部关闭、关机、进入待机 |
| 常见状态询问 | 现在温度多少、设备有没有开 |
| 固定兜底回复 | 没听清、设备离线、当前功能不支持 |

复杂表达再进入 LLM：

| 类型 | 示例 |
| --- | --- |
| 模糊体感 | 有点冷、太闷了、洗澡前帮我准备一下 |
| 组合意图 | 我要洗澡了、洗完了帮我收一下 |
| 售后问答 | 出现故障码怎么办、怎么清洁滤网 |
| 主动沟通话术 | 进入浴室后的简短问候和提醒 |

LLM 回复控制在 50 字以内，避免语音播报过长，也降低输出 token 成本。

### 5.3 LLM 输出格式

LLM 不允许直接输出自由文本控制硬件，必须输出结构化结果：

```json
{
  "type": "CONTROL",
  "confidence": 0.86,
  "replyText": "有点冷的话，我先帮你开弱暖。",
  "needConfirm": false,
  "actions": [
    {
      "code": "heater",
      "value": "weak",
      "durationMinutes": 30
    }
  ]
}
```

如为知识库问答：

```json
{
  "type": "QA",
  "confidence": 0.82,
  "replyText": "这个故障建议先断电重启，如仍存在请联系官方售后。",
  "sourceRefs": ["售后FAQ"]
}
```

如无法识别：

```json
{
  "type": "CLARIFY",
  "confidence": 0.3,
  "replyText": "我没太理解，你可以再说一遍要打开哪个功能。"
}
```

## 六、模型实测和费用统计

### 6.1 测试目标

本次必须拿到真实 API 调用数据，给东信展示模型效果和成本边界。测试不是只看单价，而是看每个模型在浴霸场景中的综合表现。

测试维度：

| 维度 | 说明 |
| --- | --- |
| 意图准确率 | 能否正确识别控制动作 |
| JSON 合规率 | 返回结构是否稳定可解析 |
| 安全命中情况 | 是否会生成不允许的动作 |
| 响应速度 | 平均耗时、P95 耗时 |
| token 消耗 | 输入、输出、总 token |
| 单次费用 | 按官方价格折算 |
| 年费用估算 | 按 10 万台设备规模估算 |
| 规则命中率 | 多少请求被本地规则拦截，不进入 LLM |

### 6.2 模型范围

第一阶段不使用深度思考模型，优先测试轻量、低延迟、低成本的商用模型：

| 厂商 | 模型方向 | 测试目的 |
| --- | --- | --- |
| 阿里百炼 | Qwen Flash / Turbo | 成本低，企业采购成熟 |
| 火山方舟 | Doubao Seed Mini / Lite | 成本低，响应快，适合量产评估 |
| 百度千帆 | ERNIE Turbo | 国内合规采购对照 |
| 智谱 | GLM Air / Flash | 成本和效果对照 |
| DeepSeek | Flash 类模型 | 效果对照，注意价格和采购方式 |

最终推荐模型以真实测试结果为准。测试阶段 API 费用先按实际发生记录，后续由东信确认正式采购账号或 API Key。

### 6.3 测试语料

第一阶段建立测试集：

| 类型 | 数量 | 内容 |
| --- | --- | --- |
| 基础控制语料 | 不少于 80 条 | 照明、弱暖、强暖、换气、吹风、摆风、待机、温度调节 |
| 模糊控制语料 | 不少于 50 条 | 有点冷、太闷、我要洗澡、洗完了等自然表达 |
| 知识库问答 | 不少于 50 条 | 产品介绍、安装、使用、故障、售后、清洁 |
| 主动沟通语料 | 不少于 30 条 | 进入浴室、温湿度提醒、运行提醒 |
| 安全边界语料 | 不少于 30 条 | 强暖、长时间运行、故障状态、不明确表达 |

### 6.4 成本控制机制

系统内置成本控制：

1. 离线语音命令优先由设备本地处理；
2. 在线简单命令先由服务器关键词和规则处理；
3. 常见问答可缓存，不重复调用 LLM；
4. 复杂问题才进入 LLM；
5. LLM 输出限制 50 字以内；
6. 后台记录每次调用的模型、token、耗时和费用；
7. 后台展示日费用、月费用、单设备平均费用；
8. 可设置单设备每日 LLM 调用上限和系统总费用提醒。

量产成本向东信说明时，重点展示两个数字：

- 实际进入 LLM 的比例；
- 每台设备每年的 LLM 平均成本。

## 九、主动沟通设计

主动沟通由服务器判断和生成，设备只负责上报事件和播报结果。

### 9.1 触发输入

| 输入 | 来源 |
| --- | --- |
| 有人进入 | 雷达/人感 |
| 有人离开 | 雷达/人感 |
| 停留时间 | 服务器根据事件计算 |
| 温度、湿度 | 设备状态上报 |
| 当前模式 | 设备状态上报 |
| 最近播报时间 | 服务器日志 |
| 用户主动沟通开关 | 小程序或后台配置 |

### 9.2 第一阶段场景

| 场景 | 处理方式 |
| --- | --- |
| 进入浴室问候 | 有人进入后，根据温度和用户模式生成一句简短问候 |
| 环境提醒 | 温度低、湿度高、空气闷时询问是否需要弱暖或换气 |
| 运行提醒 | 强暖运行较久或人离开后仍运行时提醒切换或关闭 |

涉及执行动作时，默认先问用户确认，不直接执行高功率动作。

### 9.3 频率控制

主动沟通必须有频率限制：

- 同一场景短时间内不重复播报；
- 安静模式减少主动播报；
- 夜间默认减少播报，具体时段可配置；
- 用户关闭主动沟通后不再触发主动话术。

## 十、知识库设计

知识库用于产品问答和售后辅助。第一阶段采用轻量 RAG，不做复杂知识平台。

流程：

```text
后台维护资料
  |
  v
分类和切分
  |
  v
检索相关片段
  |
  v
LLM 基于资料生成回答
  |
  v
记录问题、答案、引用和未命中情况
```

规则：

1. 只基于东信确认资料回答；
2. 没有资料时提示联系官方售后；
3. 涉及拆机、维修、安全风险时引导官方售后；
4. 未命中问题进入后台问题清单，后续补充资料。

## 十一、安全和稳定设计

### 11.1 控制安全

所有设备动作必须经过安全规则：

| 规则 | 说明 |
| --- | --- |
| 动作白名单 | 只允许系统定义过的动作 |
| 设备在线检查 | 离线不下发控制 |
| 故障阻断 | 有故障码时阻断取暖等高风险动作 |
| 温度范围 | 温度设定限制在设备支持范围 |
| 高风险确认 | 强暖、长时间运行、模糊意图需要确认 |
| 频率限制 | 防止重复下发同一指令 |
| 模型输出校验 | JSON 不合规或置信度低时不执行 |

### 11.2 系统稳定

服务端需要具备：

- 模型调用超时控制；
- 模型失败时降级回复；
- 设备控制失败记录；

## 十四、验收方式

本阶段以现场演示和测试记录为主。

验收场景：

1. 浴霸样机接入服务器，后台可看到在线状态；
2. 对浴霸说话后，系统能识别主要控制意图；
3. 照明、弱暖、强暖、换气、吹风、摆风、待机等主要动作可联调；
4. 小程序可查看状态并完成常见控制；
5. 后台可维护知识库并完成问答测试；
6. 雷达/人感可触发主动沟通；
7. 高风险或不明确动作可拦截或要求确认；
8. 后台可查看模型调用 token、耗时和费用；
9. 提交测试记录和问题清单。

验收限定：

- 样机联调以主要动作为准；
- 不承诺覆盖所有浴霸功能和所有异常状态；
- 不承诺所有用户表达都能一次识别准确；
- 东信未提供的资料，不纳入知识库必达范围；
- 硬件、主控、离线语音芯片本身稳定性不属于乙方单独责任。
