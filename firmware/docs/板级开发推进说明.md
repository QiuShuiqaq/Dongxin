# 东信智能浴霸固件板级开发推进说明

## 1. 当前定位

当前固件工程同时支持两类开发板：

| 开发板 | 定位 | 当前状态 |
|---|---|---|
| ESP32-C3 SuperMini | 低成本主目标，后续验证量产可行性 | 已完成 WiFi、设备注册、心跳、状态上报基础链路 |
| ESP32-S3 音频屏幕开发板 | 音频、屏幕、传感器验证板 | 已整理板级引脚资料，已加入板级自检入口，音频和屏幕驱动尚未接入 |

C3 和 S3 不共用一套写死的引脚代码。工程通过板级 profile 区分能力，避免把 S3 的音频和屏幕依赖带入 C3 量产路径。

## 2. 当前已经落地的固件能力

### C3

- WiFi STA 连接；
- 向 QiuAI Gateway 注册设备；
- 定时发送心跳；
- 定时上报设备状态；
- 设备状态结构已包含开关、照明、取暖、换气、吹风、摆风、除湿、温度、湿度、人感和故障码字段；
- UART 主控通信已具备 32 字节帧生成和校验代码，但默认关闭，等待东信确认 TX/RX 引脚和最终帧定义；
- C3 构建已通过，生成文件为 `firmware/build/dongxin_heater.bin`。

### S3

- 已整理 ES8311、ST7789、FT6206、XL9555 和传感器的板级信息；
- 已加入两条 I2C 总线扫描；
- 后续可在上电日志中确认开发板实际响应的 I2C 地址；
- 当前没有直接启用音频、屏幕和传感器驱动；
- S3 需要独立的 ESP32-S3 编译目标和 Xtensa 工具链。

## 3. 当前尚未实现的能力

以下内容不能认为已经完成：

- 麦克风采集；
- 本地唤醒词和离线固定指令；
- 在线 ASR 音频上传；
- TTS 音频播放；
- LLM 对话链路；
- S3 屏幕显示；
- 真实雷达/人感传感器读取；
- 与东信主控板的真实 UART 联调。

当前 `voice_engine` 仍是初始化桩代码。先完成板级硬件自检，再接入音频驱动，避免在引脚、Codec 和音频时序未验证前直接写完整语音链路。

## 4. 板级选择方式

配置文件：

`firmware/main/app_config.h`

未显式定义 `DX_TARGET_BOARD` 时，工程会根据当前构建目录的 ESP-IDF 目标自动选择板型：

```c
#define DX_BOARD_C3 0
#define DX_BOARD_S3 1
```

C3 构建目录使用 `esp32c3` 目标时自动选择 C3。S3 构建目录使用 `esp32s3` 目标时自动选择 S3。只有在需要强制覆盖目标时，才在构建参数或配置中显式定义 `DX_TARGET_BOARD`：

```c
#define DX_TARGET_BOARD DX_BOARD_C3
```

工程已增加编译期校验。ESP-IDF 目标芯片和 `DX_TARGET_BOARD` 不一致时会直接编译失败，避免误烧录。

## 5. 当前需要准备的内容

### 5.1 你这边需要提供

1. C3 开发板接入电脑后的实际串口号；
2. S3 开发板接入电脑后的实际串口号；
3. C3 烧录测试使用的 2.4GHz WiFi 名称和密码；
4. 运行后端电脑的局域网 IPv4 地址，固件不能使用 `localhost` 或 `127.0.0.1`；
5. 东信主控板 UART 的 TX/RX 对应关系；
6. 东信最终确认的通信帧定义，包括帧头、长度、命令字段、参数字段、校验方式和帧尾；
7. C3 外接麦克风、扬声器、显示屏和传感器的实际型号及接线方式。

WiFi 密码不要发到聊天记录中，直接填写到本地 `app_config.h` 后烧录即可。

### 5.2 当前电脑环境需要补充

当前 D 盘工具目录已确认存在 C3 的 `riscv32-esp-elf` 工具链，但没有发现：

```text
xtensa-esp32s3-elf
```

因此目前可以编译 C3，不能在本机编译 S3。无需重新安装 ESP-IDF，只需在现有 D 盘 ESP-IDF 工具环境中补充 ESP32-S3 对应的 Xtensa 工具链。

## 6. 推荐推进顺序

### 第一步：C3 基础烧录验证

1. 将 C3 接入电脑；
2. 在 `app_config.h` 填写 WiFi 和后端局域网地址；
3. 编译；
4. 烧录；
5. 打开串口监视器；
6. 确认 WiFi、设备注册、心跳和状态上报日志；
7. 在平台设备页面确认设备在线。

### 第二步：C3 与东信主控板联调

1. 先不接浴霸强电部分，只接通信接口；
2. 先验证串口接收和发送；
3. 再验证单个低风险动作；
4. 逐步加入照明、换气、吹风、弱暖、强暖、摆风、温度和待机；
5. 最后验证状态回传和故障码。

### 第三步：S3 板级自检

1. 补充 ESP32-S3 编译工具链；
2. 使用独立 S3 配置和构建目录；
3. 烧录板级自检固件；
4. 查看 I2C0 和 I2C1 扫描日志；
5. 确认 XL9555、ES8311、触摸和传感器实际地址；
6. 再接入背光、扬声器静音控制、ES8311 音频和 LCD。

### 第四步：语音链路验证

顺序固定为：

```text
麦克风采集
  -> 本地唤醒/固定指令
  -> 在线音频上传
  -> ASR
  -> 在线规则判断
  -> LLM
  -> 安全规则
  -> UART 控制
  -> TTS
  -> 扬声器播放
```

每一步单独验证成功后再连接下一步。这样出现问题时，可以明确判断是硬件、音频、网络、ASR、LLM、协议还是播放链路的问题。

## 7. 当前最重要的判断

ESP32-C3 适合承担：

- WiFi 通信；
- 与服务器交互；
- 固定指令或关键词兜底；
- 音频数据传输；
- UART 主控桥接；
- 简单状态采集和上报。

ESP32-C3 不适合承担：

- 通用离线 ASR；
- 本地 LLM；
- 大型语音模型推理；
- 复杂音频算法堆叠。

S3 开发板可以用于验证完整音频输入输出和屏幕交互，但不能据此直接承诺 C3 量产硬件具备相同的本地音频能力。最终量产能力必须以 C3 实际接入的麦克风、扬声器、Codec 和内存余量为准。
